# Message 模块修复需求

## 范围

修复 message 模块审计中除“内部可信发布接口 XSS”之外的问题，覆盖消息状态并发、查询筛选、请求校验、缓存、收件箱批处理、Quartz 对账、WebSocket 通知、前端 ID 契约和 SQL 文档。

## 约束与非目标

- `SysMessageApi.publishToUsers` 的调用方按可信后端模块处理，本次不增加 HTML 清洗。
- 当前只实现 `IN_APP` 通道，不提前实现外部通道 outbox。
- 不把现有 JSON 接收范围整体迁移为按用户预展开的投递表；在现有数据模型内控制查询和批处理成本。
- 保留工作区中与本任务无关的已有改动。

## 验收条件

1. 当编辑、重排、撤回、删除与 Quartz 到期发送并发发生时，系统应串行化同一消息的状态变更，不得把已发送状态覆盖回待发送，也不得按旧发布时间发送。
2. 当管理端传入发布日期范围时，消息分页应按左闭右开的日期范围过滤。
3. 当创建或更新消息时，系统应拒绝非正数、空元素、超量接收 ID；全部接收范围应持久化为空接收值。
4. 当人工定时消息的发布时间不晚于当前时间时，系统应返回明确校验错误。
5. 模板详情和未读数缓存应有有限 TTL 作为一致性兜底；人工消息详情不得缓存已经解析出的文件访问域名。
6. 当用户执行全部已读或清空时，系统应以有界分页处理消息 ID，不得一次性加载全部历史 ID。
7. 当 Quartz 对账运行时，系统应补齐或重排有效任务，并清理 message 任务组内不再对应待发送消息的孤儿任务。
8. 当消息范围发生变化时，WebSocket 通知应避免逐在线用户查询角色和部门；客户端仍应通过收件箱接口做最终可见性校验。
9. 当处理雪花 ID 时，前端 message 相关类型应统一使用 `SystemMessageApi.Id`。
10. SQL 表注释应与实际消息状态枚举一致。
11. 上述行为应有聚焦单元测试；真实 MySQL JSON、Redis TTL/失效及 JDBC JobStore 行为应明确区分为集成验证。
